## 积分与供应商成本的口径

仓库当前界面按 **1 积分＝1,000 microPoints** 展示。供应商 1 元＝1,000,000 microCny；这两种微单位不能混为一谈。

Runtime 当前计算规则为：先按实际输入、缓存输入、输出与推理桶的价格快照分别向上取整，得到供应商成本 C；用户账务按下式计算：

```text
用户扣点 microPoints = max(
  ceil(C_microCny × userRateBps / 10,000) + fixedCapabilityFeeMicroPoints,
  minimumChargeMicroPoints
)
界面扣点 = 用户扣点 microPoints / 1,000
```

预算采用 `userRateBps=15,000`（1.5 倍）、固定能力费和最低扣点为零；2026-10-29 已只读确认当前线上策略也使用这三个值。例如供应商实际 0.10 元对应 150 积分；旧方案 14 元供应商上限若直接换算，将达到 21,000 积分，不能把它当成 14 积分。这是本次收紧预算的原因，不是积分兑换人民币的承诺。任何实际策略不同、额外能力费用或报价超过上限，先重列方案，不自动执行或放大额度。

2026-10-29 核对的 [DeepSeek 官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)：Flash 每百万缓存未命中输入空闲／高峰为 1／2 元，缓存命中 0.02／0.04 元，输出 4／8 元；旧 `deepseek-v4-flash` 别名当前由 `DeepSeek-V4.1-Flash-1017` 提供服务。预算按高峰档保守计算；执行必须冻结实际服务端模型及价格快照，核对推理桶，不能重复计算已包含在输出中的 token。154,000 总 token 按最高 8 元／百万保守核算约 1.232 元，阶段预算另留取整余量；框架、导演、交接、自检及返工都须计入 token 和金额，不能另加隐藏用量。

仓库账户账本还有每日 5,000 积分暴露上限与最多四份活动预占的限制；线上函数状态已读，但这两个数值仍需与将执行的制品核对。每日暴露包含已扣和未释放预占，本次 2,450 积分不能保证在已有消费之后仍可运行。只用剩余额度，不通过临时换号、补点或改配置绕过限制。

## 必须经过的真实账务链路

```text
指定消费账号登录 Studio
  → 托管 Runtime 验证用户、应用、能力及冻结价格
  → 服务端核对本次／整轮积分和供应商预算
  → account-api 为真实任务预占 AI 积分
  → 正常队列与 Worker 调用服务端模型
  → 保存供应商请求 ID、实际 token 与用量回执
  → account-api 按实际用量结算并释放差额
  → Studio 显示真实任务／余额／账务状态
  → 用任务 ID 核对钱包预占、结算、释放和退款流水
```

使用现有 `ai_points_metered` 账务，归属 `appId=advjs-studio`、`scope=studio-managed-ai`。客户端只持用户访问令牌；`reserveAiPointsForTask`、`settleAiPointsForTask` 和 `releaseAiPointsForTask` 由 Runtime 内部通过专用服务身份调用，不给客户端或本地评测脚本私下扣款权限。

只为即将派发的真实任务按服务端报价预占。制作组总预算是派发上限，不再额外扣一笔母任务费；导演、自检、总结与返工均算真实子任务。派发前要求本轮已扣＋所有在途预占＋本次报价不超过本阶段上限，供应商暴露也要独立核对。正常钱包预占随任务释放差额：例如预占 200 积分、实际结算 30 积分，最终应只减少 30 积分，170 积分恢复可用；流水不能展示为实扣 200。

B/C 必须走同样的真实钱包链路。现有 `creative-evaluation-live-binding.mjs` 的 `createLocalCreativeEvaluationStorage` 只是隔离账本，单 Agent 的 `createCreativeEvaluationModel` 也直接调用 SDK；两者均不能用于本次扣点验收。需要先补齐受控的 B 评测任务接入及 C 的真实服务接线，统一服务端预算与用量回执；不能在直接 API 生成后补写一笔钱包扣费，伪装成完整链路。

## 成功、取消和异常如何扣费

| 结果                                 | 用户积分处理                                             | 供应商成本及后续动作                                           |
| ------------------------------------ | -------------------------------------------------------- | -------------------------------------------------------------- |
| 余额／预算／权限不足，尚未派发       | 不调用模型，不产生消费；已确认无派发的预占按协议释放     | 记录拒绝原因，不提高预算重试                                   |
| 返回有效结果并确认用量               | 按冻结价格结算实际积分，释放预占差额                     | 记录实际成本；内容质量不满意不自动免单                         |
| 排队时取消、确认尚未派发             | 释放预占，实扣为零                                       | 核对无供应商调用后结束                                         |
| 调用已在途后取消                     | 取消是停止后续任务；已确认的有效用量仍可能结算           | 等待原请求回执，不重新提交模型请求                             |
| 截断／结构解析失败                   | 按当前任务引擎规则释放用户预占，不能声称作品成功         | 仍保留已确认供应商用量和成本，并计入本次供应商上限             |
| 供应商响应未知、结算超时或流水不一致 | 明确标记待对账，不填零、不重复扣点、不擅自释放未确认预占 | 停止后续阶段，按原任务／幂等键只读核对及恢复；不自动生成第二次 |
| 已结算后符合退款规则                 | 仅走关联原任务的退款流水；是否退款依明确规则和证据决定   | 保存原消费与退款，不用赠分／余额调整掩盖消费                   |

本批预算不包含人为制造收费故障后再补跑的额外调用。断线、重复查询和重连检查复用同一个任务；若需要另外增加取消或故障样本，先从尚未执行阶段中明确重分配预算，或者另列方案。
