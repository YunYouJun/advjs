# adv-review

`adv-review` 是 ADV.JS 的剧本质量审查 Skill，让 AI Agent 像「资深编辑做 code review」一样，对章节或整个项目做**内容质量**审查并给出可执行的修改建议。

- v0.1：角色口吻一致性、对话自然度、节奏、选择质量、设定一致性等 9 维 rubric

## 定位：审「质量」，不审「结构」

`adv-review` 判断**写得好不好**，不重复检查结构正确性——那是 `adv-debug` 的职责，且是确定性的。

| 关注点                                                          | 归属                   |
| --------------------------------------------------------------- | ---------------------- |
| 语法错误、`@角色`/`【场景】` 引用缺失、死分支、孤立场景、可达性 | **adv-debug**（事实）  |
| 角色口吻、对话自然度、节奏、选择质量、情感曲线、设定一致性      | **adv-review**（判断） |

**始终把 adv-debug 的输出当作事实基准。** 不要凭自己的阅读断言结构问题——如果 `adv check` / `adv debug` 说分支能解析，那它就是能解析。你的工作从它们的确定性结束处开始。

## 命令

| 命令                                            | 说明                            |
| ----------------------------------------------- | ------------------------------- |
| `adv context [--root] [--full] [--chapter <n>]` | 加载世界观 / 角色 / 术语 / 大纲 |
| `adv check [--root]`                            | 获取结构有效性事实              |
| `adv debug branches <script> --format=json`     | 单章节分支图（判断选择/分支用） |
| `adv debug coverage [script] --format=json`     | 覆盖率指标（判断分支平衡用）    |

## 工作流

```
1. Ground  → 先跑 adv check + adv context --full + adv debug coverage 拿到事实
2. Scope   → 选定范围（优先单章节深审）
3. Review  → 按 9 维 rubric 逐项审查，每条都引用原文 + 给具体改写
4. Report  → 输出结构化报告，必须修复项排在最前
```

## 9 维评分 rubric

每维用三级评级并附具体证据：**✓ 良好 / ⚠ 可改进 / ✗ 需修复**。

1. **角色口吻一致性**（核心）—— 每句对话是否符合该角色 `.character.md` 的 `personality` / `speechStyle` / `concept`？遮住 `@角色名` 还分得清谁在说话吗？
2. **对话自然度** —— 是否有「直白说出本该暗示的情绪」、「人物互相告知双方都知道的信息（为读者服务的解说）」、翻译腔。
3. **叙述质量（show vs tell）** —— 是「她很伤心」式的 tell，还是用动作/感官/潜台词 show？是否与相邻对话冗余？
4. **节奏** —— 解说倾倒、场景过长/过短、长段落只有对话或只有旁白。
5. **选择质量** —— 借 `adv debug branches` 看选项去向：是否存在「伪选择」（读起来不同但导向相同内容，区别于 adv-debug 已检出的死选项）、含糊的代价、明显的「正确答案」。
6. **分支平衡** —— 从覆盖率 JSON 看各分支是否发育均衡，还是一条丰满一条是桩。
7. **情感曲线** —— 章节是否有「转折」（张力/关系/赌注的变化）。
8. **设定/术语一致** —— 是否与 `glossary.md` / `world.md` 矛盾，同一实体名称是否统一。
9. **伏笔与回收** —— 范围内的伏笔是否回收、回收是否有铺垫（跨章节回收标「待回收」即可，不算错误）。

## 抑制误报（重要）

路线图特别强调这一点——一个噪音多的审查者会被无视。下结论前：

1. **结构问题交给 adv-debug**：凡是引用断裂、死分支、可达性问题，直接放弃，那不是你的判断。
2. **口吻问题必须对照 `.character.md` 验证**：引用你认为被违背的那条特质，没有卡片就不下结论。
3. **尊重刻意的风格**：碎句、木讷可能是设计。世界观/角色设定能解释时，不要当 bug 报。
4. **不要臆造设定**：设定没写到的，是开放问题，不是「不一致」。
5. **宁缺毋滥**：3 条犀利的意见胜过 20 条吹毛求疵。

## 报告格式

```markdown
# 剧本质量审查：<章节 / 项目>

## 总评

<2–3 句：最大亮点、最大改进点、整体成熟度>

## 评分

| 维度           | 评级  | 一句话理由 |
| -------------- | ----- | ---------- |
| 角色口吻一致性 | ✓/⚠/✗ | …          |
| …（其余 8 维） | …     | …          |

## 必须修复

1. **[维度] 位置** — 问题
   - 现状：`引用原文`
   - 建议：`具体改写`

## 可以更好

- …

## 亮点

- …
```

## 与其他 Skill 配合

- **adv-debug** —— 先跑，拿结构事实，避免重复劳动和误报
- **adv-create** —— 用 `edit_chapter` / `edit_character` 应用采纳的修改
- **adv-story** —— 重新播放修订后的分支验证效果
