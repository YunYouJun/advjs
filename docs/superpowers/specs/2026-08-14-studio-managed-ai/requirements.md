# ADV.JS Studio 托管 AI 与 Beta 点数账本需求

## 1. 背景

ADV.JS 需要为两类使用方式建立清晰边界：

- **ADV.JS Studio** 面向 ToC Web/PWA 用户，提供由云乐坊统一运营、登录、模型路由和成本控制的托管 AI 创作服务。
- **ADV.JS Editor** 面向本地与离线生产力工作流，保持开源开放，并允许用户通过 BYOK 接入本地 AI Agent 或模型服务。

当前 Studio 的 AI 调用、模型设置、登录方式和创作生成器尚未形成统一的运行时边界；云乐坊已有 SSO、云币钱包和 CloudBase 基础设施，但还缺少面向 AI 微额消耗的可审计点数账本。

## 2. 目标

1. 为 Studio 建立统一的托管 AI 入口，隐藏供应商密钥与模型选择。
2. 使用云乐坊 SSO 统一用户身份，并以 CloudBase 作为首期服务端基础设施。
3. 使用持久化任务与 SSE 提供可恢复的流式生成体验。
4. 建立足够安全、但不过度设计的 Beta AI 点数账本。
5. 保证 AI 生成结果必须经过预览、差异确认和用户主动应用，不能直接修改项目。
6. 为未来 Editor 本地 Agent 与 Studio 云端 Agent 共用抽象保留演进空间。

## 3. 首期范围

### 3.1 仓库边界

- `YunYouJun/advjs`
  - Studio 托管 AI 客户端、内部 Agent 抽象、任务交互与提案应用流程。
  - Editor 本地/BYOK 边界保持独立。
- `YunLeFun/www.yunle.fun`
  - `cloudfunctions/ai-gateway`：统一 AI 请求入口、模型调用、任务执行、SSE 事件和用量上报。
  - `cloudfunctions/account-api`：AI 点数账户、预占、结算、释放、退款和查询。
- `YunYouJun/admin`
  - Beta 白名单、任务与用量查询、限额与熔断状态、审计入口。
- `@yunlefun/sso`
  - 复用现有 SSO v3 能力，不在本需求中重新实现身份系统。

### 3.2 首发终端

- Studio Web/PWA。
- Editor 本地开发与离线工作流。
- 原生桌面客户端不属于首期范围。

## 4. 用户故事

### 4.1 Studio 创作者

作为 Studio 创作者，我希望登录云乐坊账号后直接使用 AI 创作能力，不需要理解模型、供应商和 API Key，以便稳定地生成和修改作品。

### 4.2 Editor 本地用户

作为 Editor 本地用户，我希望继续使用自己的模型 Key 或本地 Agent（例如 Codex），以便在离线或自主管理成本的环境中工作。

### 4.3 云乐坊运营者

作为云乐坊运营者，我希望能够控制模型、价格、提示词版本、用户额度和平台总成本，并能够审计每次点数变化。

### 4.4 ADV.JS 维护者

作为 ADV.JS 维护者，我希望 Studio 云端运行时与 Editor 本地运行时共享稳定的核心任务契约，但不让 Vue、Pinia、CloudBase 或具体模型侵入核心抽象。

## 5. 功能需求与验收标准

### R1. 产品与 BYOK 边界

Studio 的生产环境 AI 能力必须统一使用云乐坊托管服务；Editor 必须继续支持本地/BYOK 工作流。

验收标准：

1. 当普通用户进入 Studio 生产环境时，系统不得展示或要求填写模型 API Key。
2. 当 Studio 发起生产 AI 请求时，客户端不得直接调用 DeepSeek 或其他模型供应商，也不得接收供应商密钥。
3. 当开发者在本地调试 Studio 时，系统可以通过非用户可见的开发适配器使用 BYOK，但该适配器不得进入生产用户设置。
4. 当用户使用 Editor 本地模式时，系统应允许配置 BYOK 或连接本地 Agent，且不得强制登录云乐坊。

### R2. 云乐坊统一身份

Studio 托管 AI 必须使用云乐坊 SSO 身份，并在首期兼容 Studio 对 CloudBase 数据、资产和协作能力的现有直接访问。

验收标准：

1. 当未登录用户调用 Studio 托管 AI 时，系统应引导其完成云乐坊 SSO 登录。
2. 当 SSO 登录完成时，Studio 应获得可供现有 CloudBase 客户端能力使用的有效会话。
3. 当用户身份不可验证或会话过期时，AI Gateway 应拒绝创建收费任务。
4. Studio 应逐步移除面向用户的独立短信登录入口，但迁移期间不得破坏已有项目访问。

### R3. 托管 AI Gateway

所有 Studio 生产 AI 调用必须经过统一的 `ManagedAgentGateway` 和云乐坊 `ai-gateway`。

验收标准：

1. 当 Studio 调用文本生成、剧情规划、章节生成、角色扮演、内容一致性检查、内容抽取或 Embedding 时，系统应通过统一 Gateway 执行。
2. 当请求到达服务端时，供应商、模型、价格版本、提示词版本和能力开关应由服务端决定。
3. 当 CloudBase 已有适合的托管模型时，Gateway 应优先通过 CloudBase 模型服务调用。
4. 当任务属于确定性单次或多次模型调用时，系统不得为了统一形式而强制使用 CloudBase Agent Runtime。
5. 当任务确实需要工具调用、长链路状态或 Agent 编排时，Gateway 应允许路由至 CloudBase Agent Runtime。
6. 当图片、TTS 或 ASR 没有可接受的托管实现时，Studio 生产环境应隐藏对应入口；浏览器本地 Web Speech 能力可以保留。

### R4. 持久化任务与 SSE

AI 任务状态必须以服务端持久化记录为真源，SSE 只负责实时投影。

验收标准：

1. 当用户提交 AI 请求时，系统应先创建持久化任务，再开始调用模型。
2. 当任务执行时，客户端应通过 SSE 接收状态、文本增量、候选结果、用量摘要和终止事件。
3. 当 SSE 断开或页面刷新时，客户端应能重新读取任务记录并恢复当前状态，而不是将断线等同于任务失败。
4. 当同一用户已有运行中的 AI 任务时，首期系统应拒绝或排队新的并发任务，使用户并发数不超过 1。
5. 当任务被取消时，服务端应停止继续向客户端推送，并尽力终止未完成的上游调用。

### R5. 提案、预览、应用与撤销

Agent 不得直接修改用户项目；所有修改必须以可审查提案交付。

验收标准：

1. 当 Agent 生成项目修改时，系统应返回结构化提案、影响文件和可读差异。
2. 当用户尚未确认应用时，项目文件不得发生持久化修改。
3. 当用户确认应用时，系统应通过统一项目工作区接口写入修改，并保留撤销所需的信息。
4. 当提案无法解析或无法安全应用时，系统应保持项目原状并返回可理解的失败状态。

### R6. Beta AI 点数单位与账户

首期 AI 点数是云乐坊平台级的细粒度 AI 消耗单位，但只发放测试赠送额度，不开放充值或云币兑换。

固定换算关系：

- `1 云币 = ¥0.1`
- `1 云币 = 100 AI 点`
- `1 AI 点 = 1000 microPoints`
- `1 云币 = 100,000 microPoints`

验收标准：

1. 当系统保存余额、预占和结算金额时，必须使用整数 `microPoints`，不得使用浮点数保存账务金额。
2. 当客户端展示余额和消费时，应将 `microPoints` 转换为 AI 点。
3. 当 Beta 用户首次获得测试额度时，系统应通过一笔可审计的赠送交易增加余额。
4. 首期系统不得实现积分批次、过期、消费优先级、付费充值或云币自动兑换。
5. AI 点数应是云乐坊平台级账户，并通过 `appId`、`scope` 和 `taskId` 区分 ADV.JS 等不同应用的消耗。

### R7. 预占、结算与退款

每个可能产生模型成本的任务必须先预占额度，再按实际用量结算。

验收标准：

1. 当任务预计所需额度超过可用余额时，系统应在调用模型前拒绝任务。
2. 当任务开始执行时，系统应原子地将预计额度从可用余额移动到预占余额。
3. 当任务成功产生可用候选结果时，系统应按供应商返回的实际用量结算，无论用户之后是否点击应用。
4. 当用户取消已产生部分内容的任务时，系统应按取消前已产生的实际用量结算，并释放剩余预占额度。
5. 当平台错误、上游错误、解析错误或安全拦截导致任务没有可用候选结果时，系统不应扣除用户点数，并应释放全部预占额度。
6. 当系统自动重试请求时，自动重试产生的额外成本应由平台承担，不得重复向用户计费。
7. 当用户主动点击重新生成时，系统应创建新任务并按新任务独立计费。
8. 当预占、结算、释放或退款请求被重复提交时，系统应通过幂等键保证余额只变化一次。

### R8. 最小可审计账本

首期账本必须保持简单，同时具备可追溯和可对账能力。

验收标准：

1. 系统应维护 AI 点数账户、不可变交易流水和 AI 用量记录三类数据。
2. 每笔交易应包含用户、应用、任务、交易类型、变更量、变更后余额、幂等键和时间。
3. 每条用量记录应包含供应商请求标识、模型、输入/输出/缓存/推理等实际用量分项、价格快照、成本、用户结算金额和任务结果。
4. 交易流水一经完成不得原地修改；修正必须通过新的冲正或调整交易完成。
5. 系统应能够按用户、应用、任务、模型和日期聚合用量与点数消耗。
6. 系统应能够将用户账本汇总与 CloudBase 供应商侧总用量进行定期对账，并标记差异。

### R9. 内容安全与收费边界

Studio 可以支持正常虚构作品中的成熟主题，但必须阻止明确违法或高风险内容。

验收标准：

1. 当内容涉及未成年人色情、非自愿色情或其他明确禁止内容时，服务端应阻止生成或交付。
2. 当内容仅为正常虚构作品中的成熟、暴力或情感主题且不触发禁止规则时，系统不应一概拒绝。
3. 当安全检查阻止任务且没有交付可用候选结果时，系统不得扣除用户点数。
4. 当任务被安全策略阻止时，客户端应收到稳定的原因代码和适度说明，不应暴露内部审核规则细节。

### R10. Beta 风险控制

首期必须通过服务端策略限制用户和平台成本。

验收标准：

1. 当用户不在 Beta 白名单中时，系统应拒绝其使用 Studio 托管 AI。
2. 当用户单日已创建 20 个计费任务时，系统应拒绝新的计费任务。
3. 当用户单日已消耗 500 AI 点时，系统应拒绝新的计费任务。
4. 当平台当日实际供应商成本达到 ¥50 时，系统应触发硬熔断并拒绝新的模型调用。
5. 运营者应能够在服务端关闭全部 AI、单个模型或单项能力，而无需发布新的 Studio 客户端。
6. 限额判断必须在服务端执行；客户端展示不得作为安全控制依据。

### R11. 内部 Agent 抽象与发布边界

首期应先在 Studio 内部形成可测试的 Agent 契约，不立即发布 `@advjs/agent`。

验收标准：

1. Agent 核心契约不得依赖 Vue、Pinia、CloudBase SDK 或具体模型 SDK。
2. Studio 云端适配器应实现统一契约，并允许未来增加 Editor 本地适配器。
3. 在 Editor 本地运行时和 Studio 云端运行时都形成真实稳定用例之前，不应发布公共 `@advjs/agent` 包。
4. 现有剧情大纲、章节、情节、角色扮演和一致性检查等入口应逐步迁移到该内部契约，避免继续直接依赖模型设置 Store。

### R12. 运营与审计

运营者必须能够在不读取用户供应商密钥的前提下观察系统用量和处理账务异常。

验收标准：

1. 当运营者查询任务时，后台应展示任务状态、用户、应用、能力、模型、用量、供应商成本和用户点数消耗。
2. 当需要人工补偿或修正时，后台应创建带操作人、原因和关联任务的调整交易，不得直接覆盖账户余额。
3. 当发生超额、重复请求、账本差异或供应商异常时，系统应保留足够的请求标识和审计信息用于定位。
4. 首期不得把 Orb、OpenMeter、Lago、Stripe、Langfuse 或 LiteLLM 放入扣点关键链路；后续观测系统只能作为账本事件的下游消费者。

## 6. 非功能要求

### 6.1 安全

- 供应商密钥只能存在于服务端受控环境。
- AI 点数写操作只能由可信服务端执行，浏览器不得直接写账本集合。
- 所有跨服务调用必须验证用户身份、应用身份和请求幂等键。
- 日志和外部观测数据不得包含完整作品正文、密钥或不必要的个人信息。

### 6.2 一致性

- 余额变化与交易流水必须在同一原子边界内完成。
- 任务、用量和交易之间必须能够通过稳定标识关联。
- SSE 丢失、客户端重试和函数重入不得造成重复任务或重复扣费。

### 6.3 可用性

- 流式连接失败不得导致已完成任务结果丢失。
- 平台熔断时应快速失败并返回明确的可重试状态。
- 服务端策略变化不得要求 Studio 客户端同步发布。

### 6.4 可测试性

- 预占、结算、释放、取消、自动重试、手动重生成和幂等路径必须具备自动化测试。
- Gateway 的模型调用必须可以使用测试适配器替换，不应在普通测试中产生真实模型费用。
- 至少覆盖一个从 SSO 身份到任务完成、SSE 恢复、点数结算和提案应用的端到端场景。

## 7. 非目标

首期明确不包含：

- Studio 面向普通用户的 BYOK。
- 原生桌面客户端。
- AI 点数购买、云币兑换、转让或反向兑换。
- 积分批次、到期规则、订阅套餐、发票和收入确认。
- 将所有 AI 请求强制迁移到 CloudBase Agent Runtime。
- 公共发布 `@advjs/agent`。
- 将第三方计量或可观测平台作为账本真源。
- 首期恢复没有受控托管实现的图片、TTS 和 ASR 功能。

## 8. 发布约束

1. 规格、设计和任务拆分必须依次确认后才能开始实现。
2. 代码实现与生产资源变更应分开验收。
3. 任何生产 CloudBase 集合、权限、模型开通、云函数部署和流量切换都必须经过单独的上线确认。
4. Beta 默认以白名单和成本硬上限保护，不得直接对全部 Studio 用户开放。
